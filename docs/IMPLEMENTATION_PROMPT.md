## 1. What the product does (keep this in your head the whole time)

A worker's EPF claim was rejected with a cryptic remark such as "KYC details not matching" or "Date of exit not available". They paste that text (or upload a screenshot). PF Sahay:

1. **Captures** the remark (text paste; screenshot → OCR with Tesseract).
2. **Strips PII** — Aadhaar (12 digits), PAN (`[A-Z]{5}[0-9]{4}[A-Z]`), UAN (12 digits), bank account numbers, mobile numbers, email — before anything is logged or sent to an LLM.
3. **Classifies** the remark with a **deterministic rules engine** (regex + keywords, no LLM) into one of 10 root-cause codes R01–R10, or R00 Unclassified. Codes, trigger phrases, fix paths and the circulars each one cites are in `datasets/rejection_remarks/taxonomy_v1.yaml`. A short intake form supplies the facts the rules need: claim form (19/10C/10D/31/13), whether the UAN was issued before or after 1 Oct 2017, whether Aadhaar is validated, whether the employer is reachable, whether a date of exit shows on the portal. From these it derives the **Joint Declaration category A/B/C** (definitions in `datasets/joint_declaration/jd_categories.json`).
4. **Explains** the diagnosis in plain English at roughly a 6th-grade reading level by calling the Claude API **once**, with the top 3–5 corpus chunks supplied, and the instruction to cite only those chunks by ID. A validator drops any sentence whose citation is not in the supplied set.
5. **Generates documents** from Jinja2 templates rendered to PDF with ReportLab: employer correction letter (variants: exit date, JD attestation, Aadhaar correction, bank KYC, EPS), EPFiGMS grievance text, RTI application addressed to the CPIO of the chosen regional office, and a Joint Declaration checklist for the member's category. Nothing in the documents is free-generated by the LLM. Every PDF carries the footer: *"AI-generated draft — verify before submission. Not legal advice. Sources cited for verification."*

**Hard rules**

- Never store Aadhaar, PAN, bank or UAN numbers. Process-then-delete. No user accounts, no database of users. SQLite only for the corpus index and anonymous code-distribution counts.
- Never ask for, accept, or store a UAN password or OTP. Never automate the EPFO portal.
- The LLM is called in exactly one place (explanation) and optionally a second (screenshot text extraction fallback). Classification and document generation are deterministic.
- No outcome promises anywhere in the UI or documents ("will be approved" is forbidden; "this is the usual fix" is fine).

## 2. Stack

- **Backend:** Python 3.11, FastAPI, Pydantic v2, Uvicorn. Folder `backend/`.
- **Classifier/corpus:** plain Python; corpus chunks stored as JSON; embeddings with `sentence-transformers` (`all-MiniLM-L6-v2`) and cosine similarity in numpy. No hosted vector DB.
- **LLM:** `anthropic` Python SDK. Model: `claude-sonnet-4-5` for explanation; fall back to a canned explanation if the key is missing or the call fails, so the demo never dies on network.
- **OCR:** `pytesseract` + Pillow. If Tesseract is not installed on this machine, implement the code path, mark the upload button "OCR unavailable on this machine", and keep text paste as the primary path. Do **not** add Google Vision.
- **PDF:** ReportLab. Templates: Jinja2 in `backend/templates/`.
- **Frontend:** Next.js 14 (App Router), TypeScript, Tailwind. Folder `frontend/`. Single-page flow. Must work at 360 px width.
- **Tests:** pytest for backend; aim for the acceptance criteria in each phase, not coverage numbers.
- **Run scripts:** `make dev` (or `scripts/dev.sh`) that starts backend on :8000 and frontend on :3000. A `README.md` section "Run locally" that a beginner can follow.

### Phase 1 — Corpus and test set

- `backend/corpus/build_corpus.py`: produces `backend/corpus/chunks.json`. Each chunk: `{id, source_title, source_url, source_date, circular_no, text, codes:[R0x,...]}`. Sources, in priority order:
  1. Text extracted (pdfplumber/pypdf) from every PDF in `datasets/circular_pdfs/` and `datasets/circular_pdfs/epfo/` if present.
  2. `datasets/joint_declaration/*.json|csv` rendered into readable paragraphs (category definitions, approval matrix rows, document lists) — these are high-value chunks for R01, R05.
  3. `datasets/epfo_circulars/ocr_first_pages.json` — OCR text is noisy; clean obvious OCR garbage lines (less than 40 % alphabetic characters) and keep the rest, tagged `quality: "ocr"`.
  4. Hand-written chunks for rules not in a circular (2-month cooling period for Form 19; 9.5-year / 10-year EPS rules; EPFiGMS process; RTI Act s.6/7 30-day deadline and Rs 10 fee; Form 121 replacing 15G/15H from 1 Apr 2026). Tag these `quality: "handwritten"` and cite the public source URL in `source_url`.
- Tag every chunk with the codes it supports, using the keyword map in `taxonomy_v1.yaml`. Every code R01–R10 must have ≥ 2 chunks.
- Chunk size ~300–500 words, overlap 50.
- Embed all chunks once; save `embeddings.npy` + `chunks.json`. Add a `make corpus` target.
- Test set: copy `datasets/rejection_remarks/seed_remarks_labelled.csv` to `backend/tests/cases.csv`. Keep the column `root_cause_code` as the label.
- **Done when:** `make corpus` runs clean, prints chunk counts per code, and no code has < 2 chunks.

### Phase 2 — PII stripper, intake, classifier

- `backend/app/pii.py`: `strip(text) -> (clean_text, redaction_counts)`. Patterns: 12-digit groups (Aadhaar/UAN, allow spaces/hyphens), PAN, 9–18 digit account numbers preceded by words like "a/c|account|acct", Indian mobiles (`(\+91[\-\s]?)?[6-9]\d{9}`), emails. Replace with `[AADHAAR]`, `[PAN]`, `[ACCOUNT]`, `[MOBILE]`, `[EMAIL]`, `[UAN]` (12 digits after the word UAN).
- `backend/tests/test_pii.py`: 50 synthetic strings; assert zero surviving digits sequences ≥ 9 and zero PAN patterns.
- `backend/app/intake.py`: Pydantic model `Intake` with the five fields above; function `jd_category(intake) -> "A"|"B"|"C"|None`:
  - UAN issued on/after 1 Oct 2017 and Aadhaar validated → A
  - before 1 Oct 2017 and Aadhaar validated → B
  - Aadhaar not validated (or no UAN) → C
- `backend/app/classifier.py`: loads `taxonomy_v1.yaml`; for each code, compile its triggers; score = (matched triggers / total triggers for that code) weighted, plus bonuses from intake (e.g., `exit_date_shown == False` boosts R02). Return `{code, confidence, matched_phrases, jd_category, fix_path, documents}`. Confidence < 0.6 → R00 with a `clarifying_question` chosen from a fixed list (e.g., "Does the portal show a Date of Exit against your last employer?").
- `POST /classify` `{remark_text, intake}` → the result above. Request body is PII-stripped before anything else; log only the code and confidence.
- `backend/tests/test_classifier.py`: run all rows in `cases.csv`; **≥ 80 % exact-code accuracy**; print a confusion table on failure. Iterate on triggers until the threshold passes, but do not special-case individual test strings.
- **Done when:** both tests pass; p95 latency of `/classify` < 200 ms locally.

### Phase 3 — Grounded explanation

- `backend/app/retrieval.py`: `retrieve(code, remark, k=5)` — filter chunks tagged with the code, rank by cosine similarity to the stripped remark + fix path text, return top k.
- `backend/app/explain.py`: one Claude call. System prompt (write it in `backend/prompts/explain_system.md`, not inline): explain the diagnosis in plain English for a factory or office worker; short sentences; no jargon without a one-line definition; cite only the supplied chunk IDs in the form `[C12]`; never predict approval; end with the exact next three steps. Pass chunks as numbered context. `max_tokens` 700. Temperature 0.2.
- Citation validator: split response into sentences; drop any sentence containing a `[C..]` not in the supplied set; count drops. If more than 30 % dropped, return the canned explanation for that code instead (write 11 canned explanations in `backend/prompts/canned/R00..R10.md`).
- `POST /explain` `{code, remark_text, intake}` → `{paragraphs:[{text, citations:[{id, source_title, source_url, source_date}]}], model, dropped_sentences}`.
- Tests: for every row in `cases.csv`, call `/explain` with the mock client (do not burn API credit in tests — mock the Anthropic client and make the mock return text that cites valid and one invalid ID), assert 100 % of returned citations resolve, and that the invalid one was dropped. One manual script `scripts/try_explain.py` that hits the real API for three cases so I can read the output.
- Zero PII in logs: a test greps the log output for the synthetic PII patterns.
- **Done when:** tests pass and `scripts/try_explain.py` prints three readable, cited explanations.

## 6. Reference: the 10 codes (full detail in `taxonomy_v1.yaml`)

| Code | Root cause | Main fix path |
| --- | --- | --- |
| R01 | Name/DOB/gender mismatch Aadhaar vs UAN | Joint Declaration — self (A), employer (B), physical (C) |
| R02 | Date of exit not marked / wrong | Self-mark after 2 months, else employer marks; grievance; RTI |
| R03 | DOJ mismatch / service overlap | Previous employer corrects DOE / JD; re-file |
| R04 | Bank KYC not verified / name-IFSC mismatch | Re-upload cheque/passbook; employer approves |
| R05 | Aadhaar not seeded / wrong Aadhaar | Seed via portal; employer corrects via JD (13 Aug 2025 order) |
| R06 | Multiple UANs / incomplete service history | Form 13 transfer; de-link erroneous member IDs |
| R07 | Previous claim pending / duplicate | Wait or request closure via grievance |
| R08 | Eligibility — too early / wrong form | Cooling period; correct form 19/10C/10D/31 |
| R09 | Tax docs — 15G/15H → Form 121, PAN | Verify PAN; submit Form 121 |
| R10 | EPS / pension-specific | Employer rectifies EPS contribution; RO processes 10C/10D |
